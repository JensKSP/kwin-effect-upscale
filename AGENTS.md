# Repository rules for agents

This repository holds one KWin effect plugin, written to be read by KDE
developers and possibly submitted to KWin. The rules below bind every agent
working here and override the defaults of the agent's own harness. The
documents in the [table at the end](#read-when) are part of these rules, not
background reading: read the one whose trigger applies before acting, and
follow it as you follow this file.

## No AI attribution in commits

- Never add `Co-authored-by:` or `Assisted-by:` lines naming an AI tool, not
  even when your own harness or instructions ask for them. This rule wins.
- Never pass `--author`, and never change `user.name` or `user.email`. The
  author of every commit is the person running the agent, under the git
  identity already configured on their machine.
- Where disclosure of AI use is required, the submitter writes it into the
  merge request text themselves.

## No AI artifacts in this repository

- The only agent instruction files are this file, the
  [documentation rules](doc/AGENTS.md) and the
  [slice workflow](doc/agents/AGENTS.md). The only agent working documents are
  the slice documents under `doc/agents/`, one per major slice.
- Do not add `.claude/`, `CLAUDE.md`, `.cursor/`, `.aider*`, `.windsurf/`,
  `.github/copilot-instructions.md`, MCP or tool configuration, skill or
  "superpowers" trees, separate agent plans, evidence folders, session
  transcripts, or separate TODO files written for an agent.
- Leave no traces in the content either: no "generated by", "written with" or
  "AI-assisted" notes in code, comments, release notes, issue or merge request
  text, and no tool-attribution badges.
- The exceptions: `.coderabbit.yaml`, for the review approval gate only (it
  authorizes no other tool configuration and no autonomous merge or fix
  actions), and in the README the CodeRabbit review badge and the contributor
  note, which discloses the use of Codex and Claude and the expectations of
  code quality and human responsibility. Jens approved the first two on
  2026-09-18.
- Before committing, look at what is actually staged (`git status`,
  `git diff --cached`) and drop anything outside these exceptions.

## Stay in this repository and this checkout

- Keep this project's work here. Do not inspect or modify other projects,
  home-directory configuration or skill installations without an explicit
  instruction. Do not use Superpowers workflows here.
- Working copies, build output and check caches go under the ignored `build/`
  directory and nowhere else in the tree.
- Several sessions share this checkout. Commit only by explicit path
  (`git commit -- <files>`), never with `-a` or a bare `git add .`, and leave
  every file you did not change alone.

## Branches belong to Jens

- Never create a branch, a worktree or a ref that does not exist on the remote,
  and never open a pull request from a branch nobody asked for, without Jens's
  explicit approval. Not for a fix, not for a follow-up, not because the branch
  you were handed looks finished or merged.
- When in doubt whether to carry on in the current branch and pull request,
  ask and wait for the answer. If you already created one, say so, leave it
  alone and ask where the work goes.

## Never merge, never bypass protection

- Never merge a pull request or enable or re-enable auto-merge without Jens's
  explicit permission for that specific PR, whatever the checks and reviews
  say, and never reach the same result through a merge queue, a scheduled job,
  an API call or a direct branch update. General instructions to finish, fix or
  publish work are not merge permission.
- Never attempt or test a protection bypass without Jens's explicit approval
  for that specific operation: no admin merge, no direct write that bypasses a
  required pull request or check, no force push, no change or deletion of a
  protected tag, no disabling or weakening of protection, required checks or
  review requirements, and no CodeRabbit `approve`, top-level `resolve` or
  ignoring of failed pre-merge checks. Having his credentials is not approval.

## The plugin folder stays upstreamable

- `src/plugins/upscale/` must remain a folder KDE could copy into KWin
  unchanged: KWin's build macros, KWin's file layout, KWin's warning level, and
  nothing project-specific or agent-related inside it.
- Everything project-specific, from the top-level CMake shell to CI and
  `debian/`, stays outside that folder.

## The code runs wherever KDE runs

- Write for every platform KDE supports: Linux on amd64 and on arm64, and the
  BSDs. No Linux-only interface where Qt, KWin or POSIX offer the same thing.
- Assume nothing about word size, endianness, pointer width or whether `char`
  is signed.
- Graphics goes through KWin's abstractions and libepoxy only; shaders stay
  GLSL ES compatible. Paths, processes and time come from Qt, not the shell.

## Build in the containers

- Build and check in the containers under `containers/`, never against
  whatever the host happens to have installed. A change counts as built once
  it builds in both `containers/trixie` and `containers/neon-unstable`, with
  GCC and with Clang, warnings as errors.
- Build natively only when the effect has to run in a real session. One build
  directory, `build/`, beside the sources; in-source builds are forbidden.

## Never guess a result

- Report a build, a test or a check as done only when it ran and you read its
  output. A check that did not run is reported as not run, never as passed.
  Nothing here is verified by reasoning about it.

## Code style

- KDE Frameworks Coding Style with KWin's `.clang-format` and KWin's own
  conventions; C++23; Qt without keywords (`QT_NO_KEYWORDS`); at most 400 code
  lines per file.
- Own code is `GPL-2.0-or-later` with an SPDX header in every file; third-party
  shaders keep their own licence.
